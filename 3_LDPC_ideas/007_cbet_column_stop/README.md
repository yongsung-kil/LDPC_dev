# 007 cbet_column_stop: 열 단위 조기 종료 CB-ET

출처: ieee:6865738 (2014 학회) | 상태: 실패 (기존 PCRC 대비 순증 절감이 전 구간 음수, -7.2%에서 -14.0%)

## 📌 요약

- **논문 아이디어**:
    - **조기 종료**: LDPC 복호가 수렴하면 최대 반복 횟수를 다 채우지 않고 멈추는 기능
    - 기존 조기 종료는 **iteration**(모든 column block을 한 바퀴 도는 반복 단위)이 끝날
      때만 수렴을 확인함
    - 논문은 **column block**(열 블록, 한 번에 처리하는 열 묶음)을 하나 처리할 때마다
      확인하자고 제안함 (CB-ET, column-based early termination)
    - 판정 재료는 디코더가 이미 들고 있는 패리티 검사 상태라 추가 연산이 거의 없음
- **제안 이유**:
    - 수렴은 iteration 중간에 일어나는데 기존 기법은 iteration 끝까지 기다림
    - 열마다 확인하면 수렴 직후의 남은 column 처리를 아낄 수 있음
    - 평균 수렴 iteration이 작은 저에러 영역일수록 마지막 iteration의 부분 절감 비중이 커짐
- **성공시 효과**:
    - 프레임당 처리 column block 수(연산량과 전력의 대리 지표)가 기존 종료 기준보다 줄어듦
    - 논문은 iteration 경계 종료 대비 처리량 21.8-37.7% 개선을 보고함
    - 이 코드베이스에는 **PCRC**(partial cyclic redundancy check, 정보 비트의 CRC를
      iteration 중간 4개 지점에서 확인하는 기존 조기 종료)가 이미 있으므로, 실질 판정
      기준은 PCRC 대비 순증 절감임
- **개선 확인방법**:
    - 한 번의 실행에서 종료 기준 3개(iteration 경계, PCRC 모사, CB-ET)의 정지 조건이
      처음 성립한 자리를 프레임별로 기록해 처리 column block 수를 비교함
    - **기록 전용 측정**: 실제 복호 판정은 그대로 두고 자리만 기록하므로 FER는 변하지 않음
    - 상세는 아래 평가 계획 표
- **실험 결과**:
    - **판정: 실패** (측정한 HD min-sum 영역 기준)
    - CB-ET의 iteration 경계 대비 절감은 0.1-5.4%, 기존 PCRC 모사는 6.8-12.8%. 그래서
      PCRC 대비 CB-ET 순증은 <span class="worse">전 구간 음수 (-7.2%에서 -14.0%)</span>
    - 원인은 **CSW**(check sum weight, 패리티 검사 위반 수)의 지연: 이 코드베이스의
      check sum은 V2C extrinsic 부호 기반이라 판정 비트가 다 맞은 뒤에도 CSW가 늦게 0에
      닿음 (genie 수렴 시점까지 CSW가 0에 닿지 않은 프레임 <span class="worse">71-96%</span>)
    - 확인 주기를 column 단위로 좁혀도 이 지연을 뒤집지 못함
    - 안전성은 확인됨: 거짓 정지(정보 비트에 에러가 남았는데 정지) <span class="better">15,000
      프레임에서 0건</span>. 다만 이득이 없으면 추가할 이유가 없음
    - 측정 범위 밖: C++의 BF 1-4회 구간은 py에 BF 모드가 없어 측정하지 않음 (BF 구간은
      CSW 지연이 작을 수 있어 재측정 가치 남음)

#### 지표별 해석

1. **PCRC 모사 대비 CB-ET 순증은 전 구간 음수** (<span class="worse">-7.2%에서
   -14.0%</span>):
    - CB-ET가 성립한 프레임만 보면 저에러 쪽에서는 CB-ET가 더 이른 경우가 많음 (E=10:
      성립 292프레임 중 PCRC가 더 이른 것은 35)
    - 그러나 성립 프레임 자체가 포인트당 4.3-29.2%뿐이라 전체 평균은 PCRC가 앞섬
    - E=40 이상에서는 성립 프레임 안에서도 대부분 PCRC가 먼저임 (E=40: 성립 191프레임
      중 187)
2. **원인은 CSW의 지연**:
    - 이 코드베이스의 check sum은 V2C(variable to check) 메시지의 extrinsic(자기 edge
      기여를 뺀 값) 부호 기반임
    - 판정 비트가 전부 맞아진 뒤에도 edge 부호들이 정렬될 때까지 CSW가 0에 닿지 않음
    - 실제로 genie 성공 시점까지 CSW가 0에 닿지 않은 프레임이 71-96%였음 (CB-ET 미성립 열)
    - 즉 CSW == 0은 "정보 비트가 다 맞음"(PCRC가 보는 것)보다 훨씬 늦은 사건이고, 확인
      주기를 column 단위로 좁혀도 이 지연을 뒤집지 못함
3. **CB-ET의 iteration 경계 대비 절감도 0.1-5.4%에 그침**:
    - 미성립 프레임은 두 기준에 같은 하한값이 들어가므로 이 수치는 성립 프레임의 마지막
      iteration 부분 절감만 반영한 값
    - 기존 PCRC가 경계 대비 6.8-12.8%를 이미 가져가는 것과 대비됨
4. **안전성 자체는 확인됨**:
    - 정보 비트 기준 거짓 정지 <span class="better">0건</span>
    - 다만 정지 순간 codeword 전체(패리티 포함) 기준 오류가 남아 있던 프레임이 15000개
      중 4개 있었음
    - check sum이 posterior(판정 비트)가 아니라 extrinsic 부호 기반이라 CSW == 0이
      H x (판정 비트) = 0과 완전히 같지는 않다는 뜻. 하드웨어 적용 시 CRC 확인
      결합(메모 4절)이 필요한 또 하나의 근거
5. **논문 경향(저에러일수록 이득 증가)**은 경계 대비 수치에서는 재현됐으나 (E=10에서
   5.4%로 최대), PCRC 대비 순증을 뒤집을 크기가 아님

## ✅ 결론

- **판정: 실패** (측정한 HD min-sum 영역 기준)
- **근거**:
    1. 이 코드베이스에는 iteration 내부 4지점 정지(PCRC)가 이미 있고, CB-ET의 판정
       재료인 CSW는 PCRC가 보는 정보 비트 수렴보다 늦게 0에 닿음. 그 결과 PCRC 모사
       대비 순증 절감이 전 구간 음수(-7.2%에서 -14.0%)
    2. 확인 주기를 column 단위로 좁히는 것(논문의 기여)은 판정 재료가 늦게 익는 문제를
       해결하지 못함. 메모 4절이 추정한 순증 상한(지점 세분화로 iteration의 약 1/8)은
       CSW 지연에 가려 실현되지 않음
    3. 거짓 정지 0건으로 안전성은 논문 보고와 일치하나, 이득이 없으면 추가할 이유가 없음
- **측정 범위 밖**:
    - C++의 BF(bit flipping) 1-4회 구간은 PCRC 정지가 제한되어 CB-ET가 새로 여는
      영역이지만(메모 4절), py BaseDecoder에 BF 모드가 없어 이번 측정에 포함되지 않음
    - BF 구간은 1bit 모드라 V2C 부호가 판정 비트와 같아 CSW 지연이 여기보다 작을 수 있음
