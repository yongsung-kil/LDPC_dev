007 CB-ET column 단위 조기 종료 (그림자 측정)

출처: ieee:6865738 | 상태: 1단계 그림자 측정 완료

📌 요약

  • 논문이 제안하는 것: LDPC 복호가 수렴하면 최대 반복 횟수를 다 채우지 않고 멈추는 조기 종료를, iteration(전체 column block을 한 바퀴 도는 반복 단위) 경계가 아니라 column block(열 블록) 경계마다 판정하자는 제안이다 (CB-ET, column-based early termination). 판정 재료는 디코더가 이미 들고 있는 패리티 검사 상태라 추가 연산이 거의 없다
  • 왜 효과가 있다고 보는지: 수렴은 iteration 중간에 일어나는데 기존 기법은 iteration 끝까지 기다린다. 열마다 확인하면 수렴 직후의 잔여 column 처리를 아낄 수 있고, 평균 수렴 iteration이 작은 저에러 영역일수록 마지막 iteration의 부분 절감 비중이 커진다
  • 성공하면 무엇이 바뀌는지: 프레임당 처리 column block 수(연산량과 전력의 대리 지표)가 기존 종료 기준보다 줄어든다. 논문은 iteration 경계 종료 대비 처리량 21.8-37.7% 개선을 보고했다. 이 코드베이스에는 PCRC(partial cyclic redundancy check, 정보 비트의 CRC를 iteration 중간 4개 지점에서 확인하는 기존 조기 종료)가 이미 있으므로, 실질 판정 기준은 PCRC 대비 순증 절감이다
  • 무엇으로 확인하는지: 한 번의 실행에서 종료 기준 3개(iteration 경계, PCRC 모사, CB-ET)의 최초 발화 좌표를 프레임별로 기록해 처리 column block 수를 비교한다 (그림자 측정이라 FER 불변). 상세는 아래 지표 계획 표

📄 출처 상세

  • 논문: "High-Throughput QC-LDPC Decoder with Cost-Effective Early Termination Scheme for Non-Volatile Memory Systems" (2014 학회)
  • 핵심 아이디어: block-serial layered min-sum 복호와 겹쳐 돌며 패리티 검사식을 column 단위로 누적 검사해 sub-iteration 경계에서 종료. 검사 회로는 XOR 레지스터와 permuter, OR 트리뿐 (면적 2.2% 증가)
  • 적용 분석 메모: ../_pm/tasks/전력감축_논문정독/메모_ieee6865738_CBET.md

바꾼 것

  • 디코더: decoder.py의 CbEtShadowDecoder, 재정의 함수: _run_iteration (C++ 대응: 메인 루프. 종료 로직 계측은 교체용 함수 6개에 해당하지 않아 새논문적용규칙 2절 3항 적용). _init_state와 _build_result는 기록 버퍼 추가용 확장이고 산술은 전부 부모 것이다

  • ㉮ iteration 경계 종료: CSW == 0을 iteration 끝에서만 확인 (논문의 비교 대상)
  • ㉯ PCRC 모사: 정보 column 구간(130개)을 4등분한 지점(column 32, 65, 97, 130번째 처리 직후)에서 genie 정보 비트 오류 0을 확인 (CRC 통과의 근사)
  • ㉰ CB-ET: 매 column 처리 직후 running CSW == 0 확인
  • 실제 종료 판정은 BaseDecoder와 동일 (그림자 측정). run.py --verify로 같은 입력에 대한 판정 결과가 BaseDecoder와 완전히 같음을 확인했다

지표별 해석:

  • ㉮ PCRC 모사 대비 CB-ET 순증은 전 구간 음수다 (-7.2%에서 -14.0%). CB-ET가 발화한 프레임만 보면 저에러 쪽에서는 CB-ET가 더 이른 경우가 많지만 (E=10: 발화 292프레임 중 PCRC가 더 이른 것은 35), 발화 프레임 자체가 포인트당 4.3-29.2%뿐이라 전체 평균은 PCRC가 앞선다. E=40 이상에서는 발화 프레임 안에서도 대부분 PCRC가 먼저다 (E=40: 발화 191프레임 중 187)
  • ㉯ 원인은 CSW의 지연이다. 이 코드베이스의 check sum은 V2C(variable to check) 메시지의 extrinsic(자기 edge 기여를 뺀 값) 부호 기반이라, 판정 비트가 전부 맞아진 뒤에도 edge 부호들이 정렬될 때까지 CSW가 0에 닿지 않는다. 실제로 genie 성공 시점까지 CSW가 0에 닿지 않은 프레임이 71-96%였다 (CB-ET 미발화 열). 즉 CSW == 0은 "정보 비트가 다 맞음"(PCRC가 보는 것)보다 훨씬 늦은 사건이고, 확인 주기를 column 단위로 좁혀도 이 지연을 뒤집지 못한다
  • ㉰ CB-ET의 iteration 경계 대비 절감도 0.1-5.4%에 그친다 (미발화 프레임은 두 기준에 같은 하한값이 들어가므로 이 수치는 발화 프레임의 마지막 iteration 부분 절감만 반영한 값이다). 기존 PCRC가 경계 대비 6.8-12.8%를 이미 가져가는 것과 대비된다
  • ㉱ 안전성 자체는 확인됐다: 정보 비트 기준 거짓 정지 0건. 다만 발화 순간 codeword 전체(패리티 포함) 기준 오류가 남아 있던 프레임이 15000개 중 4개 있었다. check sum이 posterior(판정 비트)가 아니라 extrinsic 부호 기반이라 CSW == 0이 H x (판정 비트) = 0과 완전히 같지는 않다는 뜻으로, 하드웨어 적용 시 CRC 확인 결합(메모 4절)이 필요한 또 하나의 근거다
  • ㉲ 논문 경향(저에러일수록 이득 증가)은 경계 대비 수치에서는 재현됐으나 (E=10에서 5.4%로 최대), PCRC 대비 순증을 뒤집을 크기가 아니다

✅ 결론

무의미 (측정한 HD min-sum 영역 기준). 까닭:

  • ㉮ 이 코드베이스에는 iteration 내부 4지점 정지(PCRC)가 이미 있고, CB-ET의 판정 재료인 CSW는 PCRC가 보는 정보 비트 수렴보다 늦게 0에 닿는다. 그 결과 PCRC 모사 대비 순증 절감이 전 구간 음수(-7.2%에서 -14.0%)다
  • ㉯ 확인 주기를 column 단위로 좁히는 것(논문의 기여)은 판정 재료가 늦게 익는 문제를 해결하지 못한다. 메모 4절이 추정한 순증 상한(지점 세분화로 iteration의 약 1/8)은 CSW 지연에 가려 실현되지 않았다
  • ㉰ 거짓 정지 0건으로 안전성은 논문 보고와 일치하나, 이득이 없으면 추가할 이유가 없다

측정 범위 밖: C++의 BF(bit flipping) 1-4회 구간은 PCRC 정지가 제한되어 CB-ET가 새로 여는 영역이지만(메모 4절), py BaseDecoder에 BF 모드가 없어 이번 그림자 측정에 포함되지 않았다. BF 구간은 1bit 모드라 V2C 부호가 판정 비트와 같아 CSW 지연이 여기보다 작을 수 있다.
