### P4 헤더 대 본문 신규 검사와 생성 모드

- ㉮ H6(`num_group == len(groups)`)과 G7(그룹별 행 수)를 모든 생성 경로와 전수 대조했다. 그룹이나 행 수를 바꾸는 자리는 `groups.insert/pop`, `group.insert/pop/clear/append`, `group[:] =` 를 grep해 열두 곳을 찾았고, 모두 `num_group`, `num_row_each_group`, `type_each_group`을 함께 갱신한다. 행만 더하는 `Insert_Random_Row`([DAO_Main.py:2517](../../../../SRC/DAO_Main.py#L2517))와 `Gen_LLR_Insert_Mutated_Row`([DAO_Main.py:3325](../../../../SRC/DAO_Main.py#L3325))는 `num_row_each_group[group_idx] += 1`, 행만 지우는 `_Build_Deleted_Row_Matrix` Case A([DAO_Main.py:5590](../../../../SRC/DAO_Main.py#L5590))는 `-= 1`을 한다. 그룹을 늘리고 줄이는 자리는 세 배열을 모두 다시 만든다. 갱신을 빠뜨린 모드는 없다
- ㉯ `Insert_Random_Row`가 row를 끼운 뒤 CSW 재배정에 실패해 `None`을 돌려주는 경로에서는 헤더가 갱신되지 않은 채 남지만, 그 매트릭스는 `optimal_LLR_matrix`의 Deep_Copy이고 trial마다 새로 뜨므로 다음 trial에 새지 않는다
- ㉰ 옛 형식(꼬리 전부 -1) 매트릭스 `Prime_ECC_2.3`과 `Prime_ECC_2.4`의 `LLR_MATRIX_0.txt`를 직접 읽어 `Is_LLR_Valid`를 돌렸다. 둘 다 유효하고 `has_sw_branch=False`, 묶음은 전부 홑그룹이다. H6과 G7이 옛 형식을 새로 거부하지는 않는다

### P5 CSW 보정과 HBF 경로

- ㉮ `Correct_LLR_Matrix`의 순서(배수 맞춤 → 범위 자르기 → 내림차순 정렬 → 중복 내리기)가 C3(범위), C4(8의 배수), C5(엄격 감소)를 모두 만족시킨다. 내리는 값이 `prev - STEP_CSW`라 8의 배수가 유지되고, 조건이 `>=`라 연쇄로 내려간다. 실행 확인: `[-1,100,100,100]` → `[-1,96,88,80]`, `[-1,1408,1408]` → `[-1,1408,1400]`
- ㉯ 연쇄 내리기가 `MIN_CSW` 아래로 가면 `ValueError`를 던진다(`[-1,8,8,8]`, `[-1,4,4]`에서 확인). 이 예외를 받는 호출처는 둘뿐이고 **둘 다 잡는다**. - ㉰ HBF 시퀀스 `[40, 41, 10, 11, 60]`의 다섯 값이 `GenLLRModeHBF`의 이름과 같고(INSERT_RANDOM_GROUP, INSERT_RANDOM_ROW, MUTATE_MATRIX, MUTATE_CSW, SPLIT_GROUP), `Gen_Trial_LLR`이 다섯 모드를 모두 처리한다

- ㉲ `Correct_LLR_Matrix`는 보호 구간 검사보다 뒤에 돌아 보호 구간 그룹의 값도 고칠 수 있는 자리에 있다. 입력 두 개로 직접 돌려 본 결과 바뀌는 row가 하나도 없었다(`ch_length=1`이라 CH 정렬이 무의미하고, 값이 모두 `min_value`~`max_value` 안에 있다). 지금 입력에서는 문제가 없다

### P11 묶음 변이의 파급

- ㉮ `Generate_Random_Mutation`과 `Mutate_CSW` 모두 `_Get_Target_Bundle_Groups`가 준 그룹마다 element_pool을 따로 만들고 따로 표본을 뽑는다. spec 3.7 ㉱의 "그룹마다 따로"와 맞다. `now_enable_CSW_update_limit`의 skip row 계산도 그룹마다 따로 돈다
- ㉯ `Mutate_CSW`의 `random.randint(1, max_changes)`는 기본값 `NUM_ELEMENTS_TO_MUTATE_CSW = 1`에서 늘 1이다. 그룹마다 정확히 1행을 고치고, row가 1개뿐인 그룹(파일 1의 g0, g4)은 pool이 비어 건너뛴다. 묶음이 커지면 한 trial의 CSW 변이 수가 그룹 수만큼 늘어난다(설계 의도대로)
- ㉰ 변이 대상 그룹 index는 늘 `min(target_group_indices)` 이상이다. 타겟 목록이 묶음 대표만 담고 묶음은 대표에서 시작하므로, `bundle_of_group[head]`의 원소는 모두 `head` 이상이다. MUTATE 두 모드를 보호 구간 검사에서 빼는 근거가 성립한다
- ㉱ `prev_generated_mutation`이 담은 그룹 index는 같은 stage 안에서만 쓰인다. `Gen_LLR_Mutate_Matrix`가 `current_trial_idx == 1`에서 튜닝 상태를 초기화하므로 stage를 넘어 새지 않는다
- ㉲ `max_modification_trial`은 MUTATE 모드에서 `MUTATE_CONFIG.MAX_TRIAL`(기본 -1 → 9999)이고, 튜닝 조합 수가 늘어도 trial 수 자체가 무한해지지는 않는다 (발견 6은 메모리와 stage 낭비 쪽이다)

### P14 헤더 규약과 데이터 모델

- ㉮ 헤더 0은 코드 쪽 되돌림 값으로만 나온다. `Build_SW_Branch_Layout`의 길이 불일치 대체값, `Build_Reordered_Matrix`가 `group_order`를 다 쓴 뒤 채우는 값, 죽은 `_create_reorder_test_matrix`의 restart 표시다. 저장소의 입력 네 개(`Prime_ECC_2.3`, `2.4`의 `LLR_MATRIX_0.txt`, `Prime_ECC_3.0`의 1과 2)에는 0이 없고 1, 10, 20, 21만 쓴다. H8이 10 미만을 보통 그룹으로 보는 것은 0과 1 둘 다에 맞다
- ㉯ `max_iteration`의 두 정의가 같다. `Build_SW_Branch_Layout`([DAO_LLR_MATRIX.py:119](../../../../SRC/DAO_LLR_MATRIX.py#L119))와 `Is_LLR_Valid`([DAO_LLR_MATRIX.py:606](../../../../SRC/DAO_LLR_MATRIX.py#L606)) 모두 `max(group[-1].iter_end for group in groups)`다. 모드들이 쓰는 `groups[-1][-1].iter_end`도 분기 매트릭스에서 같은 값을 낸다. G10이 한 구간의 모든 분기가 같은 끝을 덮게 강제하므로 마지막 그룹의 끝이 언제나 최대값이기 때문이다. 파일 1과 2 모두 124로 일치한다
- ㉰ `bundle_of_group`의 원소가 같은 묶음끼리 같은 리스트 객체를 가리키는 것은 문제되지 않는다. 읽는 자리 네 곳(`Initialize_Stage`, `Check_SW_Branch_Mode_Allowed`, `Set_Gen_Trial_LLR_Mode`, `_Get_Target_Bundle_Groups`) 가운데 그 리스트를 제자리에서 고치는 곳이 없다. 밖으로 나가는 두 곳은 `list(...)`로 복사해 준다. `Build_SW_Branch_Layout` 안에서는 새 묶음이 시작될 때 `current_bundle`을 새 리스트로 다시 묶으므로 앞 묶음이 오염되지 않는다
- ㉱ 새 row와 새 그룹의 꼬리 출처를 전수 확인했다. 타겟(또는 삽입 기준) 그룹에서 물려받는 여섯 자리([DAO_Main.py:2443](../../../../SRC/DAO_Main.py#L2443), [2669](../../../../SRC/DAO_Main.py#L2669), [2877](../../../../SRC/DAO_Main.py#L2877), [3305](../../../../SRC/DAO_Main.py#L3305), [3435](../../../../SRC/DAO_Main.py#L3435), [4979](../../../../SRC/DAO_Main.py#L4979))는 G9(그룹 안 꼬리 일치)와 H8을 지킨다. 어긋나는 세 자리가 발견 2, 3, 4다
- ㉲ 새 그룹의 헤더 값은 INSERT 계열이 1, SPLIT_GROUP이 타겟의 원래 값, restart가 1(살아 있는 경로)로 일관된다. SPLIT_GROUP이 타겟의 값을 물려받는 것은 분기 그룹이 타겟이 될 수 없으므로 언제나 10 미만이다
- ㉳ `Copy_Row`(COPY_ROWS)는 `ch_th_values`만 바꾸고 꼬리와 헤더를 건드리지 않는다. 발견 1의 COPY_GROUP과 달리 분기를 옮기지 않는다
