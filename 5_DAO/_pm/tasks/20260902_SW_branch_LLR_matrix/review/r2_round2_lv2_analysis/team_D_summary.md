## ㉯ 교차 분석

### D-1. 구간(span) 번호의 뜻이 파서와 디코더에서 다르다 (HIGH)

- 문제: 파서는 구간 번호를 분기 index가 0으로 되돌아온 횟수로(등장 순서로) 매기고, 문턱 배열과 `Select_BF`는 구간 0을 iteration 1~4, 구간 1을 iteration 5~8로 못박는다. 두 정의가 코드로 묶여 있지 않다
- 문서 안 위치: code_diff 3.2(236-253행), 2.2(165행), 4.1(447-449행), 5.1(560-569행), 상위 문서 5.3-1, 7장 ㉰
- 근거: `code_diff.md:246` 조건 `b == 0 && prev_branch != 0`은 파일 안 등장 순서만 본다. `code_diff.md:165, 447-449, 560-569`은 span 0에 130, span 1에 1100을 넣고 BF 진입 여부로 두 구간을 나눈다. 배경 메모 [msg1.md](../../../../../../msg1.md)`:31-34`의 예시(`1/4/-1`, `5/8/0`, `5/8/1`, `5/8/2`)를 넣으면 iteration 5~8 그룹이 구간 0이 되어, BF 진입 프레임은 5~8의 분기를 문턱 130으로 고르고 미진입 프레임은 `cur_sw_branch_idx[0]`이 초기값 0이라 syn_weight와 무관하게 분기 0으로 고정되며 분기 2는 어떤 프레임에서도 선택되지 않는다. 오류 출력도 없다
- 처방: 구간을 등장 순서가 아니라 iteration 범위로 정한다. 파서가 구간별 `iter_start`를 `PARAM_LLR`에 기록하고 `Select_BF`가 그 범위로 문턱 배열을 고르거나, 파서가 "구간 0의 시작이 1이 아니면 오류"를 낸다
- 처방의 성격: 동작 변경 있음 (3.2의 계산 로직 교체 또는 5.1이 구간 범위를 참조하도록 변경). 코드 삭제 없음
- 지적한 워커: D_1 #1, D_2 #1 (팀 P #1과도 독립 일치)
- Round 3 검증 필요: **예**. HIGH이고 처방이 두 갈래이며 동작 변경을 요구한다. `LLR_MATRIX_1.txt`가 두 구간 모두 분기를 가져 우연히 맞는 것이라 반례가 파일이 아니라 배경 메모 쪽에 있다

### D-2. 적용 순서 3단계의 전제 "`cur_sw_branch_idx[]`가 모두 0"이 성립하지 않는다 (HIGH)

- 문제: 3단계에서 6장(그룹 선택)만 넣으면 `cur_sw_branch_idx[]`를 채우는 코드가 어디에도 없어 미정의 값과 비교하게 된다. 값이 우연히 0이 아니면 iteration 1~8의 분기 그룹이 모두 후보에서 빠져 `selected_group == -1`이 되고 오류 (1)을 찍으며 row 0으로 돈다
- 문서 안 위치: code_diff 9장 3단계(999-1001행), code_diff 6.1(693행), code_diff 2.2
- 근거: `decoder.cpp:5-8`의 생성자가 부르는 `Initialize_Dec`(`decoder.cpp:19-30`)는 포인터만 NULL로 채운다. `ECC_Top`은 사용자 정의 생성자를 가지므로(`ecc_top.cpp:6-20`) `new ECC_Top()`이 값 초기화를 하지 않고, `Decoder`는 `ECC_Top`의 값 멤버다. `Clear_Flag`(`decoder.cpp:606-616`)와 4.1도 이 배열을 건드리지 않으며 채우는 곳은 5.1(4단계)뿐이다
- 리더 추가 확인: 배열이 0으로 채워져도 3단계의 검증 기준 "기존 동작과 결과가 같아야 한다"는 성립하지 않는다. 변환된 파일(type 전부 1)로 손 실행하면 옛 AUTO 루프(`decoder.cpp:6985-6999`)는 iteration 1~4에서 그룹 2, iteration 5에서 그룹 4, iteration 6~8에서 그룹 5를 고르고, 새 루프는 분기 0 조건 때문에 그룹 0, 1, 3을 고른다. 따라서 "3단계에서 기존과 결과가 달라지면 파일 읽기나 그룹 선택에 문제가 있는 것이다"라는 진단 기준이 사용자를 파서 쪽으로 오도한다
- 처방: 1단계에서 `Clear_Flag`의 612-613행을 `cur_sw_branch_idx[]` 0 채우기로 교체한다(D-3과 같은 자리). 9장 3단계의 검증 기준 문장을 "분기 0 그룹만 골라진다"로 다시 쓴다
- 처방의 성격: 코드 두 줄 삭제와 추가. 최종 동작 변경 없음(중간 단계의 미정의 값만 제거), 문서 서술은 다시 쓰기 필요
- 지적한 워커: D_3 #1(HIGH), D_1 #6(MEDIUM으로 D-3과 묶어 지적)
- Round 3 검증 필요: **예**. HIGH이고 코드 삭제를 요구하며 심각도에 워커 간 이견이 있었다

### D-3. `Clear_Flag`의 두 줄이 code_diff에 없다 (MEDIUM)

- 문제: `Clear_Flag`가 2.2에서 지우는 두 멤버에 대입하고 있어 그대로 두면 컴파일이 깨진다. 문서가 수정 전후를 전수로 싣는 형식인데 이 자리가 빠졌다
- 문서 안 위치: code_diff 2.2, code_diff 9장 1단계
- 근거: `decoder.cpp:612-613`이 `flag_HD_1_4_Set = FLAG_LOW; flag_HD_5_8_Set = FLAG_LOW;`이고, `Clear_Flag`는 프레임마다 `decoder.cpp:1091`에서 불린다. Grep 전수 결과 두 멤버의 참조는 `decoder.h:297-298`(선언), `decoder.cpp:612-613`, `2090-2091`, `2100`, `2106`, `2117`, `2123`, `7002`, `7006`, `7010`, `7016`뿐이며 이 가운데 code_diff가 다루지 않는 곳은 612-613 두 줄뿐이다
- 처방: 두 줄을 `cur_sw_branch_idx[]` 0 채우기로 교체한다 (D-2의 처방과 같음)
- 처방의 성격: 코드 삭제와 추가. 동작 변경 없음
- 지적한 워커: D_3 #2, D_1 #6
- Round 3 검증 필요: **예** (코드 삭제 요구. D-2와 묶어 한 번에 검증)

### D-4. 파일의 구간별 분기 개수와 `num_sw_branch[]`를 대조하지 않는다 (MEDIUM)

- 문제: 문턱과 분기 개수는 컴파일 상수인데 분기 개수는 파일이 정한다. 두 값이 어긋나면 오류 없이 그룹이 사장되거나 후보가 사라진다
- 문서 안 위치: code_diff 4.1(464-469, 476-477행), 6.1(691-695행), 6.2(766-770행), 상위 문서 7장 ㉰
- 근거와 경우:
  - ㉠ default 갈래는 `num_sw_branch[0] = 1`(4.1 465행)이라 `Select_SW_Branch(0, w)`가 항상 0을 돌려주고, `LLR_MATRIX_1.txt`의 그룹 2(분기 1, iteration 1~4)가 어떤 프레임에서도 후보가 되지 않는다. 이 갈래는 AUTO 빌드에서 `main.cpp:141-143`이 `argc > 19`일 때 임의 `matrix_sel`을 받으므로 도달한다 (리더가 `main.cpp:136-163`을 직접 확인)
  - ㉡ 4.1은 span 0, 1만 채우므로 세 번째 구간을 둔 파일은 `num_sw_branch[2] = 1`이 되어 그 구간의 분기 1 이상 그룹이 조용히 사장된다
  - ㉢ 파일 분기가 상수보다 적으면(구간 1에 분기 0만 있는데 `num_sw_branch[1] = 2`) `syn_weight >= 1100`인 프레임의 iteration 5~8에서 후보가 없어 오류 (1) 출력 뒤 row 0을 쓴다
  - ㉣ `num_sw_span > MAX_SW_SPAN`(4) 검사가 3.2에도 4.1에도 없어 6.1의 `cur_sw_branch_idx[span]`이 배열 밖을 읽는다
  - ㉤ `num_sw_branch`를 2 이상으로 올리면서 문턱을 빠뜨리면 그 칸은 0으로 남고 `weight < 0`이 항상 거짓이라 마지막 분기로 고정된다
- 처방: 파서가 구간별 분기 개수(서로 다른 분기 index의 수, 0부터 연속인지)를 `PARAM_LLR`에 기록하고, `Init_Dec_Option`의 4.1 코드 끝에서 `num_sw_branch[]`, `num_sw_span <= MAX_SW_SPAN`, 문턱의 양수 오름차순을 대조해 어긋나면 멈춘다. 4.1 끝의 "대조하는 검사를 넣으면"은 제안 문장이고 코드가 없다
- 처방의 성격: 코드 추가만. 조용한 오선택을 오류로 바꾸는 동작 변경 포함. `LLR_MATRIX_1.txt`와 `LAYOUT_PRIME_512B_TLC_VSS_OFF` 조합에서는 동작 변경 없음
- 지적한 워커: D_1 #4, D_2 #4, D_3 #3 (팀 P #5와도 일치)
- Round 3 검증 필요: **예**. 처방이 두 갈래(파서가 세어 채우기 대 상수 유지 후 대조)이고 다섯 워커가 독립 지적했다

### D-5. 파서의 구간 번호가 헤더 순서에 의존하고 `span = -1` 방어가 없다 (MEDIUM)

- 문제: 구간의 첫 분기 그룹의 index가 0이 아니면 `sw_span_idx_each_group`이 -1이 되고, 6.1이 `cur_sw_branch_idx[-1]`을 읽는다. 분기 0 그룹이 같은 구간의 분기 1 그룹 뒤에 오면 새 구간으로 오인한다
- 문서 안 위치: code_diff 3.2(246-249행), 6.1(692-693행), 1.1
- 근거: 3.2는 `b != SW_BRANCH_NONE`이고 `num_sw_span == 0`인 상태에서 `sw_span_idx_each_group[i] = num_sw_span - 1 = -1`을 쓴다. 6.1(692-693행)은 `span`을 검사하지 않고 첨자로 쓴다. D_1의 배치 A 손 실행에서 그룹 2를 맨 앞에 두면 구간이 하나로 합쳐지고 첫 그룹이 -1을 받는다
- 처방: 3.2에 ㉠ 첫 분기 그룹의 index가 0이 아니면 오류, ㉡ 같은 구간 안에서 index가 되돌아감 없이 작아지면 오류, ㉢ 루프 뒤 `num_sw_span > MAX_SW_SPAN`이면 오류를 넣고, 6.1에도 `span < 0 || span >= MAX_SW_SPAN`이면 건너뛰는 방어를 둔다. 다만 `local_opt.cpp:56`의 `err`는 흐름을 바꾸지 않으므로 검사가 실제로 멈추게 하는 처리가 함께 필요하다 (팀 P 영역과 겹침)
- 처방의 성격: 코드 추가만. 정상 파일 동작 불변
- 지적한 워커: D_1 #2 (팀 P #3과 일치)
- 리더 판정: D_1은 `cur_sw_branch_idx[-1]`이 앞 멤버 `syn_th_BF0`를, D_3은 `cur_sw_branch_idx[4]`가 뒤 멤버 `num_sw_branch[0]`을 읽을 것이라고 각각 적었다. 둘 다 2.2의 선언 순서에 기댄 추정이고 표준이 보장하지 않으므로 "정의되지 않은 동작"까지만 인정한다
- Round 3 검증 필요: **예** (배열 밖 접근)

### D-6. "분기 일치를 넣으면 순서에 좌우되지 않는다"는 서술이 실제 범위를 넘는다 (MEDIUM)

- 문제: 이 주장은 후보 집합(현재 분기와 같은 그룹과 분기 없는 그룹을 합친 집합) 안에서 iteration 범위가 겹치지 않을 때만 성립한다. 같은 분기 안에서 겹치거나, iteration 1~8을 통째로 덮는 분기 없는 그룹과 5~8 분기 그룹이 공존하면 여전히 뒤쪽 그룹이 이긴다
- 문서 안 위치: 상위 문서 5.3-2, code_diff 6.1 바뀐 점 ㉯(716-717행)
- 근거: 6.1의 루프는 `g = num_group - 1`부터 내려가며 첫 일치에서 `break`한다(`code_diff.md:688, 706-709`). 분기 없는 그룹은 분기 필터를 항상 통과하므로 같은 iteration을 덮는 분기 그룹과 함께 후보가 된다. 리더가 6.1 수정 후 코드를 직접 읽어 확인했다. 수정 전 AUTO 갈래(`decoder.cpp:6985-6999`)와 같은 성질이며 6.1이 새로 만든 결함은 아니다
- 처방: 문서에 전제("한 분기의 그룹들과 분기 없는 그룹을 합친 집합 안에서 iteration 범위가 겹치지 않는다")를 적고, 파서에 구간별, 분기별 범위 겹침 검사를 넣는다
- 처방의 성격: 문서 수정. 검사는 코드 추가만
- 지적한 워커: D_1 #3
- Round 3 검증 필요: **예** (단일 워커 지적이고 작성자 요청 2의 답에 직접 걸린다)

### D-7. iteration 1~4 구간의 분기 존재와 문턱 130 채택이 미결정에 없다 (MEDIUM)

- 문제: BF 진입 프레임의 iteration 1~4 분기를 syn_weight 130으로 가르는 것은 코드 어디에도 없던 새 동작인데, 근거가 주석 한 줄이고 배경 메모와도 어긋나며 미결정 목록에 올라 있지 않다
- 문서 안 위치: code_diff 2.2(172-174행), 4.1(459행), 5.1 바뀐 점 ㉯, 상위 문서 7장
- 근거: Grep 전수 결과 `syn_th_BF1`은 `decoder.h:303` 선언과 `decoder.cpp:468` 대입 두 곳뿐이고 읽는 곳이 없다(리더 직접 확인). `FLAG_HD_1_4_SET_TYPE_1`도 대입하는 곳이 없다. 단서는 `decoder.h:303`의 주석 `// S-4 Set` 하나다. 수정 전 코드는 BF 진입 시 `decoder.cpp:2090`에서 `FLAG_HD_1_4_SET_TYPE_0`으로 못박으므로, syn_weight 130 이상 680 미만에서 그룹 2를 쓰는 것은 새 동작이다. 배경 메모(`msg1.md:21-22`)는 "bf라면 llr matrix에서 threshold를 받지 않아, -1로 처리"라고 하고 예시도 `1/4/-1`인데 `LLR_MATRIX_1.txt`는 그 구간에 분기 둘을 둔다
- 처방: 상위 문서 7장에 "iteration 1~4 구간의 분기 존재 여부와 문턱 값(130 여부)"을 Decision 항목으로 올린다
- 처방의 성격: 문서 수정. 결정 결과에 따라 4.1과 5.1의 코드가 바뀔 수 있다

## ㉲ 미커버 영역

관점 4, 5, 9, 13의 확인 항목 가운데 어느 워커도 다루지 않은 것이다.

- ㉠ **BF 진입 프레임의 마지막 iteration이 그룹 선택에 미치는 영향**: `local_opt.cpp:126`이 `MN[i] -= ITER_MAX_HBF`를 적용하면 `MN[MN_num-1]`이 120이 되고 `decoder.cpp:1118`이 이를 `MN`으로 삼으므로, BF 진입 프레임은 iteration 120까지만 돌고 그룹 11의 iteration 121~124 row는 미진입 프레임만 쓴다. D_1이 2.6 ㉯에서 사실만 적고 관점 7(팀 I)로 넘겼고, 팀 D 안에서 이 비대칭이 그룹 선택과 row 사용에 미치는 영향은 판정하지 않았다
- ㉡ **SD 갈래의 `iter - 1`과 restart 지점의 어긋남**: 관점 13의 확인 항목 "8.1 호출처 `decoder.cpp:2328`이 `iter - 1`을 넘기는 점"에 대해 D_3은 이 호출이 2SD와 3SD 전용이고 HD와 1.5SD는 `iter`를 그대로 넘긴다는 것까지만 확인했다. SD 모드에서 `iter - 1`로 판정하면 파일의 `restart_iter`와 한 칸 어긋나는지는 아무도 손 실행하지 않았다
- ㉢ **2SD와 3SD에서 SW 분기를 쓰지 않는 결정의 타당성**: D_2가 이 동작이 문서에 없다는 것(D-15)은 지적했으나, 배경 메모와 DAO 사용 방식에 비추어 그 결정 자체가 맞는지는 판정하지 않았다. 관점 2(팀 I)와 걸친다
- ㉣ **파일의 그룹이 0개이거나 어느 그룹의 row가 0개인 극단 입력**에서 6.1 루프와 6.2의 `num_candidate` 처리는 어느 워커도 다루지 않았다 (팀 P도 같은 항목을 미커버로 남겼다)
