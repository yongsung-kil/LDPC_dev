### 3.2 배치 A2: 그룹 0과 1만 맞바꿈 (헤더 순서 `g1 g0 g2 g3 ...`, 분기 줄 `0 0 1 0 1 1 -1 ...`)

### 3.3 배치 B: 같은 분기 안에서 iteration이 겹치는 두 그룹 (분기 0에 X = 1~4 그룹을 추가, g0 = 1~1, g1 = 2~4와 공존)

파서 3.2의 구간은 두 순서 모두 같다 (분기 0 그룹이 연속이므로).

| 순서 | iter 3, cur[0] = 0 | iter 1, cur[0] = 0 |
|------|-------------------|-------------------|
| B1: `g0 g1 X g2 g3 ...` | g2 건너뜀, X(1~4) 선택 → X | X 선택 → X |
| B2: `X g0 g1 g2 g3 ...` | g2 건너뜀, g1(2~4) 선택 → g1 | g1 밖, g0 선택 → g0 |

판정: 좌우됨. 뒤에 놓인 그룹이 이긴다. 분기 조건은 이 겹침을 걸러 주지 않는다 (같은 분기이므로 둘 다 후보). 수정 전 AUTO 갈래(`decoder.cpp:6985-6999`)와 같은 성질이며 6.1이 새로 만든 문제는 아니다.

### 3.4 배치 C: -1 그룹과 분기 그룹이 같은 iteration을 덮음 (W = -1 그룹 1~8, B0 = 분기 0 그룹 5~8, B1 = 분기 1 그룹 5~8, 뒤는 g6~g11)

파서 3.2: W는 -1, B0는 `prev = -1`이라 구간 0, B1도 구간 0 (두 순서 모두).

| 순서 | iter 6, cur[0] = 0 | iter 6, cur[0] = 1 | iter 3 |
|------|-------------------|-------------------|--------|
| C1: `W B0 B1 g6 ...` | g6~g11 밖, B1 건너뜀, B0 선택 → B0 | B1 선택 → B1 | B1, B0 건너뜀 또는 밖, W 선택 → W |
| C2: `B0 B1 W g6 ...` | g6~g11 밖, W(1~8) 선택 → W | W 선택 → W | W 선택 → W |

판정: 좌우됨. C2에서는 분기 그룹이 영원히 선택되지 않는다. -1 그룹은 어느 분기에서나 후보이므로 분기 조건이 겹침을 걸러 주지 않는다. 또한 이 배치에서 5~8의 분기 그룹이 구간 0으로 번호가 매겨져, 5.1의 구간 0 처리(BF 경로에서만 문턱 130으로 결정, 비BF 경로에서는 0 고정)가 적용된다. 이 문제는 3.6에서 따로 다룬다.

### 3.5 배치 D: 분기 index가 `num_sw_branch[span]` 이상인 그룹 (구간 0에 Y = 분기 2 그룹 1~4 추가, `num_sw_branch[0] = 2`)

분기 줄 `0 0 1 2 0 1 1 -1 ...`. 파서 3.2: Y는 `b = 2, prev = 1`이라 구간 0, 다음 g3은 `b = 0, prev = 2`라 구간 1. 구간 번호는 정상이다.

`Select_SW_Branch(0, sw)`는 0 또는 1만 돌려주므로 (`num_sw_branch[0] - 1 = 1`이 최대) Y는 어느 위치에 있든 항상 "건너뜀"이다. iter 3에서 cur[0] = 0이면 g1, 1이면 g2가 골라지고 Y는 사용되지 않는다.

판정: 좌우되지 않음. 다만 Y가 조용히 사장되고 어떤 검사도 이를 알리지 않는다. 반대 방향(파일의 분기가 `num_sw_branch`보다 적은 경우, 예를 들어 g4와 g5를 지운 파일에서 `sw >= 1100`)은 iteration 5~8에서 후보가 없어 `selected_group = -1` → 오류 (1) 출력 → `return 0` → row 0 (그룹 0의 iteration 1 row)을 쓴다. 이것도 순서와 무관하다.

### 3.6 배치 E: 배경 메모의 예시 (`msg1.md:31-34`, 1~4는 -1, 5~8은 분기 0, 1, 2)

그룹 `Ga = (-1, 1~4)`, `Gb = (0, 5~8)`, `Gc = (1, 5~8)`, `Gd = (2, 5~8)`, 뒤는 g6~g11. 분기 줄 `-1 0 1 2 -1 ...`.

파서 3.2: Ga는 -1, Gb는 `prev = -1`이라 구간 0, Gc와 Gd도 구간 0. `num_sw_span = 1`. 즉 iteration 5~8의 분기가 구간 0이 된다.

4.1(`LAYOUT_PRIME_512B_TLC_VSS_OFF`): `num_sw_branch[0] = 2` (문턱 130), `num_sw_branch[1] = 2` (문턱 1100). 5.1: BF 경로에서 cur[0]은 sw < 130이면 0, 아니면 1이고 cur[1] = 0. 비BF 경로에서 cur[0] = 0 고정, cur[1]은 sw < 1100이면 0, 아니면 1.

| 상황 | 6.1 iter 6 훑기 | 결과 | 배경 메모의 의도 (5~8 분기는 SW 문턱 1100 계열로 결정) |
|------|----------------|------|------------------------------------------------|
| BF, sw = 100 (cur = 0, 0) | Gd 건너뜀, Gc 건너뜀, Gb 선택 | 분기 0 | 분기 0, 같음 |
| BF, sw = 500 (cur = 1, 0) | Gd 건너뜀, Gc(분기 1, 구간 0, cur[0] = 1) 선택 | 분기 1 | 분기 0 (500 < 1100), 다름 |
| 비BF, sw = 900 (cur = 0, 0) | Gb 선택 | 분기 0 | 분기 0, 같음 |
| 비BF, sw = 1500 (cur = 0, 1) | Gd 건너뜀, Gc 건너뜀 (cur[0] = 0), Gb 선택 | 분기 0 | 분기 1 또는 2, 다름 |

## 4. 항목별 확인 (㉰ ~ ㉵)

### ㉰ `cur_sw_branch_idx[span]`의 index 범위

- ㉠ `span = -1` 경로: 3.2에서 분기 그룹인데(`b != SW_BRANCH_NONE`) 아직 `num_sw_span`이 0이면 `span = 0 - 1 = -1`이다. 첫 분기 그룹의 index가 0이 아닌 분기 줄(`1 0 ...`, `-1 1 0 ...`)에서 생긴다 (3.1 배치 A의 g0'). 6.1은 `span`을 검사하지 않고 `cur_sw_branch_idx[-1]`을 읽는다. 2.2의 멤버 배치에서 바로 앞 멤버는 `syn_th_BF0`이므로 실제로는 그 값(680 또는 630)이 읽힐 가능성이 크지만 정의되지 않은 동작이다
- ㉡ `span >= MAX_SW_SPAN` 경로: 분기 index가 0으로 되돌아가는 일이 5번 있으면 `num_sw_span = 5`, 다섯째 구간은 `span = 4`가 되어 `cur_sw_branch_idx[4]`(크기 4)를 읽는다. 2.2 배치에서 바로 뒤 멤버는 `num_sw_branch[0]`이다
- ㉢ 문서에 검사가 있는지: 없다. `MAX_SW_SPAN`은 1.1의 정의, 2.2의 배열 크기, 4.1의 초기화 반복 상한에만 쓰이고 `num_sw_span`과 비교하는 곳이 3.2, 5.1, 6.1 어디에도 없다. 6.1에도 `span` 범위 방어가 없다
- ㉣ 덧붙여 5.1은 구간 0과 1만 세우므로 구간 2, 3은 초기화 값 0으로 남아 분기 0만 쓰인다 (관점 5 영역)

### ㉱ GROUP_TYPE_ITER 그룹의 row 오름차순 전제

6.1은 그룹의 첫 row `iter_start[start_idx]`와 마지막 row `iter_end[end_idx]`로 그룹 범위를 판정한다. 2.1 표의 "모든 row의 iter_start~iter_end" 열에서 확인했듯이 `LLR_MATRIX_1.txt`는 12개 그룹 모두 그룹 안 row의 범위가 완전히 같다. 따라서 첫 row의 start와 마지막 row의 end가 그룹 범위이고 전제가 성립한다. 4장 ㉮로 type을 1로 되돌리면 모든 그룹이 CSW 타입이라 6.2가 row 단위 iteration 범위를 아예 보지 않는다.

일반론으로 GROUP_TYPE_ITER 그룹의 row가 `5~8, 1~4`처럼 내림차순이면 그룹 범위가 5~4가 되어 어떤 iteration에도 걸리지 않는 죽은 그룹이 된다. 이것은 수정 전 AUTO 갈래(`decoder.cpp:6995`)와 같은 성질이고 6.1이 바꾸지 않았다. 검사는 없다.

### ㉲ `selected_group` 확정 뒤 `start_idx`, `end_idx`

6.1 수정 후 코드(678-711행)에서 `continue`(694행)는 `start_idx`, `end_idx` 계산(697-705행)보다 앞에 있다. 따라서 건너뛴 그룹은 두 값을 건드리지 않고, `break`(708행)는 계산 직후이므로 루프를 나온 시점의 두 값은 선택된 그룹의 것이다. `selected_group`이 -1로 남는 경우 두 값은 마지막으로 계산된(건너뛰지 않은) 그룹의 것이거나 초기값 0이지만, 6.2가 769행에서 먼저 `return 0`하므로 쓰이지 않는다.

수정 전 비AUTO 갈래(`decoder.cpp:7038-7046`)의 재계산은 하드코딩 갈래(7001-7020)가 두 값을 계산하지 않아서 필요했던 것이다. 수정 후는 모든 갈래가 루프 안에서 계산하므로 재계산이 필요 없다. 수정 전 AUTO 갈래(6985-6999)와 구조가 같다. 문제 없음.

### ㉳ iteration 0

- ㉠ `decoder.cpp:1143-1145`: `mn == 0`이면 `cur_set_idx = 0`이고 `Get_Cur_LLR_Idx_FILE`은 불리지 않는다. row 0은 `LLR_MATRIX_1.txt`에서 그룹 0(분기 0, 구간 0, iteration 1~1, CSW -1)의 유일한 row다
- ㉡ mn 0에서 row 파라미터가 복호에 쓰이는지: `V2C_Cal`(`decoder.cpp:5699-5705`)은 HD에서 `Is_Iter_Type_Init(mn)`이 참이면 `VN_Cal_Pre`, 아니면 `VN_Cal_HD`를 부른다. `Is_Iter_Type_Init`의 AUTO 갈래(`6609-6614`)는 HD와 1.5SD에서 `iter == 0`에 참을 돌려준다 (8.2에서 이 조건은 그대로 둔다). `VN_Cal_Pre`(`3554-3623`)에는 `Get_VNU_LLR_SET_FILE` 호출이 없다 (호출 다섯 곳 `3986, 4161, 4367, 4506, 4674`는 각각 `VN_Cal_HD`, `VN_Cal_HD_HCU`, `VN_Cal_CD`, `VN_Cal_SD`, `VN_Cal_SD_HCU` 안이며, 이 다섯 함수는 `Is_Iter_Type_Init`이 거짓일 때만 불린다). HCU 갈래(`5739-5745`)도 같다. 따라서 mn 0에서 row 0의 파라미터는 복호에 들어가지 않는다. `cur_set_idx`가 mn 0에 닿는 곳은 로그(`decoder.cpp:7868`, `m_log_LLR_idx[0] = 1`)뿐이다
- ㉢ 판정: span0 = 1인 프레임에서 iteration 0이 분기 0의 row(row 0)를 가리키는 것은 문제가 아니다. 로그의 iteration 0 항목이 1(1부터 세는 row 번호)로 찍히는 것만 남는데 이는 수정 전과 같다
- ㉣ `Select_BF`는 mn 0 루프 몸체의 끝(`1968-1970`)에서 불리므로 mn 0 동안 `cur_sw_branch_idx[]`는 직전 프레임의 값이다 (첫 프레임은 문서상 아무도 초기화하지 않으므로 쓰레기 값). mn 0에서 이 배열을 읽는 곳은 `Get_Cur_LLR_Idx_FILE`(불리지 않음)과 5.1의 Corner 이벤트(`Select_BF` 안, 대입 뒤)뿐이라 해가 없다. 다만 `Clear_Flag`(`decoder.cpp:606-616`)가 매 프레임 시작(`1091`)에 불리면서 삭제 대상 멤버 `flag_HD_1_4_Set`, `flag_HD_5_8_Set`(`612-613`)을 대입하고 있는데 code_diff에 이 자리가 없다. 여기서 `cur_sw_branch_idx[]`를 0으로 초기화하는 것이 자연스럽다 (발견 6)

### ㉴ 6.2 오류 시 `return 0`

- ㉠ 호출자 `decoder.cpp:1138`은 반환값을 `cur_set_idx`에 넣을 뿐 검사하지 않는다. row 0은 BF 프레임의 iteration 1(span0 = 0)에서 정상적으로 골라지는 row이므로 (2.3 표), 호출자는 오류 반환과 정상 선택을 구별할 수 없다
- ㉡ 오류 출력 뒤 복호는 계속된다. 그 iteration은 row 0(그룹 0, iteration 1의 파라미터)으로 돈다
- ㉢ 수정 전과 비교: 수정 전은 `selected_group = -1`일 때 (1)을 출력한 뒤 `type_each_group[-1]`을 읽고(배열 밖), 대개 어느 갈래에도 안 걸려 `table_row_idx = 0`으로 (2)를 지나 0을 돌려줬다. 수정 후는 배열 밖 읽기 없이 바로 0을 돌려준다. 타입이 20, 21인 경우도 수정 전은 조용히 0, 수정 후는 (3)과 (2)를 출력하고 0이다. 복호에 들어가는 row는 양쪽 다 0으로 같다. 즉 "오류로 잡는다"(상위 5.3-3)는 출력이 붙는다는 뜻이지 복호가 멈추거나 결과가 달라진다는 뜻이 아니다. DAO 실행처럼 프레임 수가 많고 MPI rank가 여럿이면 잘못된 파일 하나에 iteration당 두 줄씩 출력이 쏟아진다

### ㉵ 파서 3.2의 구간 번호와 6.1의 `span` 사용

- ㉠ `LLR_MATRIX_1.txt`에서는 맞물린다 (2.2, 2.3). 3.2가 준 구간 0(g0, g1, g2)과 구간 1(g3, g4, g5)이 5.1의 구간 0 = iteration 1~4, 구간 1 = iteration 5~8과 일치한다
- ㉡ 일반적으로는 맞물리지 않는다. 3.2의 구간 번호는 "분기 index가 0으로 되돌아간 횟수"라 파일에서 분기가 처음 등장하는 곳이 구간 0이다. 2.2 주석(165행), 4.1 주석(447-449행), 5.1(560-569행)은 구간 0을 iteration 1~4, 구간 1을 iteration 5~8로 고정한다. 배경 메모 자신의 예시(`msg1.md:31-34`, 1~4가 -1이고 5~8에 분기 0, 1, 2)에서 두 체계가 어긋나 틀린 분기를 고른다 (3.6 배치 E). 상위 문서 7장 ㉰은 "분기 구간을 1~8로 못박을지 임의 구간을 허용할지"를 미결정으로 두었지만, 못박더라도 1~4에 분기가 없는 파일이 이미 배경 메모의 기본 예시이므로 이 어긋남은 미결정 뒤로 미룰 수 없다
- ㉢ `num_sw_span > MAX_SW_SPAN` 처리: 없다 (㉰ ㉢). `num_sw_span`은 3.2가 계산해 구조체와 MPI에 싣지만 5.1과 6.1 어디에서도 읽지 않는다

## 6. 작성자 요청 2 판정

**다음 배치에서 좌우됨**:

- ㉮ 배치 A (3.1): 구간의 첫 분기 그룹이 분기 0이 아니거나, 분기 0 그룹이 같은 구간의 분기 1 그룹 뒤에 오는 헤더 순서. 3.2의 구간 번호가 바뀌어 6.1이 다른 그룹을 고르거나 `cur_sw_branch_idx[-1]`을 읽는다
- ㉯ 배치 B (3.3): 같은 분기 안에서 iteration이 겹치는 두 그룹. 뒤에 놓인 그룹이 이긴다
- ㉰ 배치 C (3.4): -1 그룹과 분기 그룹이 같은 iteration을 덮는 배치. 뒤에 놓인 그룹이 이긴다

좌우되지 않음으로 확인한 범위:

- ㉠ `LLR_MATRIX_1.txt` 그대로: iteration 1, 2, 3, 4, 5, 6, 8, 9, 20, 124와 분기 조합 (0,0), (0,1), (1,0), (1,1), 비BF (0, span1) 전부에서 후보 집합의 iteration 범위가 서로 겹치지 않아 선택 결과가 유일하다 (2.3)
- ㉡ 배치 A2 (3.2): 같은 분기 안의 그룹끼리 순서를 바꾸는 것은 결과를 바꾸지 않는다
- ㉢ 배치 D (3.5): 분기 index가 `num_sw_branch` 이상인 그룹은 위치와 무관하게 항상 건너뛰어진다 (조용히 사장될 뿐 순서 의존은 없음)

정리하면 6.1의 분기 조건은 서로 다른 분기 사이의 순서 의존을 없애며, 그 범위에서는 문서의 주장이 맞다. 그러나 ㉠ 3.2의 구간 번호가 헤더 순서에 좌우되고, ㉡ 같은 후보 집합 안의 겹침은 여전히 순서가 정하며, ㉢ 구간 번호의 의미가 파서(등장 순서)와 디코더(iteration 1~4, 5~8 고정)에서 달라 배경 메모의 기본 예시(1~4에 분기 없음)가 틀리게 처리된다 (발견 1, 순서와 무관한 결함). 순서 독립을 보장하려면 발견 1의 구간 정의 통일과 발견 2, 3, 4의 파서 검사가 필요하다.
