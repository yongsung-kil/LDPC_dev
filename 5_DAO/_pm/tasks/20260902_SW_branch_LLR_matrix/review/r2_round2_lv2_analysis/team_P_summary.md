## ㉯ 교차 분석

### 1. 구간 번호 정의 불일치 (HIGH, P_1 #3. 팀 D의 D_1 #1, D_2 #1과 독립 일치)

- ㉠ code_diff 3.2 파서는 분기 index가 0으로 되돌아오는 곳을 새 구간으로 세어 출현 순서로 번호를 매긴다
- ㉡ code_diff 2.2 주석(165행), 4.1 주석(447-449), 5.1(560-569)은 구간 0을 iteration 1~4, 구간 1을 5~8로 고정해 `syn_th_sw_branch[0][*]`에 130, `[1][*]`에 1100(960)을 넣는다
- ㉢ 분기가 5~8에만 있는 파일(`msg1.md:31` 예시, 분기 줄 `-1 0 1 -1 ...`)에서는 파서가 5~8 구간을 구간 0으로 매기고, `Select_BF`는 BF 경로에서 `Select_SW_Branch(0, ...)`로 문턱 130을 쓴다. 비BF 경로는 분기 0으로 고정되어 분기 1, 2가 영원히 선택되지 않는다
- ㉣ 상위 7장 ㉰ "구간을 iteration 번호로 고정할지"가 미결정인데 code_diff가 두 갈래(파서는 순서, 디코더는 고정)를 동시에 택했다

판정: 세 워커(P_1, D_1, D_2)가 독립적으로 같은 곳을 지적했다. 파일이 `LLR_MATRIX_1.txt`(두 구간 모두 분기 있음)일 때만 우연히 일치한다. Round 3 검증 대상.

### 2. 파일 형태 변환 전제 미서술 (HIGH, P_1 #1, P_2 #3, P_3 #1 #2가 같은 뿌리)

- ㉠ code_diff 3.2 표, 4.1, 5장 ㉯, 6.1 표는 상위 4장 ㉮ 형태(type 전부 1, 분기 줄 추가)로 변환된 파일을 전제하고, 6.2 ㉯만 현재 파일을 전제한다
- ㉡ 현재 `LLR_MATRIX_1.txt`(type 줄 `20 20 21 ...`, 분기 줄 없음)를 3.2 파서에 그대로 넣으면 `sw_branch_idx_each_group`이 restart 줄부터 읽혀 이후 헤더가 한 줄씩 밀리고 row가 12토큰씩 어긋난다 (P_1 손계산, C_2 E-5와 일치)
- ㉢ 변환 절차와 변환된 파일 위치가 두 문서 어디에도 없고, 9장 적용 순서에 파일 준비 단계가 없다 (P_2 #3)
- ㉣ DAO 쪽에서는 형태(1)은 `Is_LLR_Valid` RW2(`floor_flag == -1` 요구)에서 거부되고, 형태(2)는 DAO 파서가 새 줄을 `num_restart`로 읽어 밀린다 (P_3 #1, #2). DAO는 어느 형태도 만들 수 없다

판정: 저장소에 있는 파일로는 code_diff의 어느 표도 재현되지 않는다. 변환 절차 명기가 처방이며 코드 변경은 없다. 팀 C(C_2 E-5)와 교차 확인됨.

### 3. 파서 범위 검사 부재로 배열 밖 접근 (MEDIUM, P_1 #5 #6 #7, P_2 #2 #4. 팀 D의 D_1 #2와 일치)

| 입력 | 결과 | 지적 |
|------|------|------|
| 첫 분기 그룹의 값이 0이 아닌 파일 (`1 0`, `-1 1 2`, 구 파일 `LLR_MATRIX_0.txt`의 `1 2 31`) | `prev_branch` 초기값 규칙으로 span이 -1로 시작해 `cur_sw_branch_idx[-1]` 읽기 | P_1 #6, P_2 #2, D_1 #2 |
| 구간이 5개 이상인 파일 | `num_sw_span > MAX_SW_SPAN` 검사 없음, `cur_sw_branch_idx[4]` | P_1 #5 |
| 분기 값이 불연속(`0 2`)이거나 `MAX_SW_BRANCH` 이상 | 검사 없음, `syn_th_sw_branch[span][b]` 범위 밖 | P_1 #7 |

P_2 #2는 구 파일 `Prime_ECC_2.4/.../LLR_MATRIX_0.txt`(분기 줄 1, 2, 31)가 정확히 첫 번째 경우임을 확인했다. 현재 3.4 대조 검사가 있는 곳(`Read_LLR_info_Auto` 안)과 `num_sw_branch[]`가 확정되는 곳(`Init_Dec_Option`, 호출 순서 `local_opt.cpp:46` → `ecc_top.cpp:229`)이 달라 대조 검사를 파서 안에 둘 수 없다 (P_2 #4).

### 4. `err` 무효와 검사 결과가 어디에도 닿지 않음 (MEDIUM 상향 근거 있음, P_1 #2, P_2 #1)

- ㉠ `local_opt.cpp:56`의 `err`는 140행 대입만 있고 읽는 곳이 없으며 함수는 void다. 3.4의 `err = TRUE`는 아무 효과가 없다
- ㉡ 3.4는 `printf`라 root 로그 파일에도 남지 않고, DAO는 `subprocess.run(check=True)`(`DAO_Main.py:7937`)로 stdout을 받지 않는다. `main.cpp:69`가 return 0 고정이라 종료 코드로도 알 수 없다
- ㉢ 결과: 헤더와 row 마지막 칸이 어긋난 파일로 DAO 최적화가 그대로 진행된다

P_2는 이 조합을 HIGH로 매겼다. 개별 사실은 MEDIUM이지만 DAO 자동 실행 경로에서는 오류가 완전히 묻히므로 보고서에서는 HIGH로 올린다.

### 5. `num_sw_branch[]` 컴파일 상수와 파일 대조 없음 (MEDIUM, P_1 #4, P_2 #4. 팀 D의 D_1 #4, D_2 #4, D_3 #3, 팀 C의 C_2 B-4와 일치)

- ㉠ 상위 4장 ㉮ "x는 읽는 쪽에서 세면 나온다"에 대응하는 코드가 code_diff에 없다
- ㉡ 4.1 default 갈래 `num_sw_branch[0] = 1`에 `LLR_MATRIX_1.txt`(구간 0에 분기 2개)를 넣으면 그룹 2가 어떤 프레임에서도 선택되지 않고 오류도 나지 않는다. AUTO 빌드에서 `main.cpp:141-153`이 argc > 19이면 임의 `matrix_sel`을 받으므로 도달 가능하다
- ㉢ 4.1 끝의 "대조하는 검사를 넣으면" 문장에 코드가 없다

다섯 워커가 독립 지적했다. Round 3 검증 대상(단일 처방이 두 갈래: 파서가 세어 채우기 vs 상수 유지 + 대조 검사).

### 6. DAO 파급과 `ITER_MAX_HBF` 척도 변경 (MEDIUM, Decision 후보, P_3 #7)

- ㉠ `decoder.cpp:1973-1978`의 `iter_num -= ITER_MAX_HBF`가 살아나 DAO가 읽는 결과 파일의 `avg_iteration` 척도가 바뀐다
- ㉡ `ecc_top.cpp:877-900`의 iteration별 FER 배열(`fr_4KB[n]`)도 `MN[i] = i - 4`가 되어 열의 뜻이 바뀐다 (팀 I의 I_1 3-5, 3-6과 같은 뿌리)
- ㉢ DAO의 우열 판정이 이 값을 읽으므로 최적화 결과가 달라질 수 있다. 상위 7장 ㉮에 DAO 파급 비용이 없다

팀 I 관점 7과 연결되며 보고서에서 하나로 합친다.

## ㉱ 미커버 영역

- ㉠ 형태(2) 파일을 실제로 만들어 3.2 파서와 DAO 파서 양쪽에 넣어 본 손계산은 P_1과 P_3가 각각 했으나, 두 파서가 같은 파일을 받을 수 있는 형태(둘 다 통과하는 헤더 배치)가 존재하는지는 답하지 않았다. DAO 파서 수정이 범위 밖으로 선언되어 있어 이 리뷰에서는 Decision으로 올린다
- ㉡ `Read_LLR_info_Auto`의 fopen 실패 시 `fscanf(NULL)` 크래시(P_2 #6)는 기존 결함이라 보고서에는 참고로만 적는다
- ㉢ 파일에 그룹이 0개이거나 row가 0개인 극단 입력은 어느 워커도 다루지 않았다 (3.1의 `new int[0]`은 P_2 #9에서 안전 확인)
