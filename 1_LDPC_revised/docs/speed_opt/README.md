# speed_opt — LDPC 디코더 속도 최적화 전달 패키지

> **이 폴더 하나가 전달 패키지다.** 다른 버전의 LDPC 코드에 같은 속도 개선을 적용하기 위한 자료 일체.
> 대상 코드는 이 저장소의 코드와 **비슷하지만 다른 버전**이라는 전제로 작성됨.

## 구성

| 파일 | 역할 |
|------|------|
| `checklist.md` | 전체 개선 항목 목록 (우선순위·bit-exact 여부·위험도 포함). 진행 상태 체크박스 |
| `commits.md` | 항목별 git 커밋 해시 누적 인덱스 (항목 = 커밋 = patch 대응표) |
| `{ID}_이름.md` | 항목별 상세 문서 — **주 지시서**. 왜 하는지 / 어디를 어떻게 바꾸는지 / bit-exact 근거 / 주의사항 / 다른 버전에서 위치 찾는 법 |
| `patches/{ID}.patch` | 이 저장소 버전 기준의 참고 diff (`original/` vs `revised/`) |

## 사용법 (다른 공간에서의 이식 순서)

1. `checklist.md`를 위에서부터 항목 하나씩 진행
2. 해당 항목의 `{ID}_이름.md`를 읽는다 — 특히 "다른 버전 코드에서 위치 찾는 법" 소절의 검색 앵커로 대상 코드에서 위치를 찾는다
3. `patches/{ID}.patch`는 **참고 구현 예시**로만 사용 — 코드 버전이 다르므로 **patch를 그대로 적용(git apply)하지 말 것**. 문서의 의미 기반 지시를 따르고, patch는 "이 버전에서는 이렇게 구현했다"의 대조용
4. 항목 하나 적용 후 검증(아래) → 통과하면 다음 항목

## 검증 방법 (모든 항목 공통)

1. Test vector 출력후 bit exact한지 확인

> 최종 FER만 보지 말 것. 중간값이 다르면 HW 검증에 못 쓰므로 **TV hex + 프레임별 iteration 수 +
> uncor 프레임 번호 + `o_overall_clk`(HW 타이밍)** 까지 비교한다.
> `[bit-exact]` 항목에서 불일치가 나면 **적용 실수**이므로, 원인을 규명하기 전에 다음 항목으로 넘어가지 않는다.

### ⚠ 예외: 6-1 / 6-2는 golden과 달라질 수 있다

이 두 항목만 성격이 다르다. 성능 개선이 아니라 **기존 코드의 미정의 동작(범위 밖 접근) 제거**라서,
기존 바이너리가 쓰레기값을 읽고 있었다면 결과가 달라지는 것이 **정상이고 새 값이 올바른 값**이다.

그래서 **적용 순서를 반드시 지켜야 한다** — 나머지 전 항목을 끝내고 bit-exact를 확인한 뒤,
맨 마지막에 6-1/6-2를 **별도 커밋으로** 얹는다. 섞으면 불일치가 났을 때 내 실수인지 원래 UB인지
구분할 수 없다. 상세: [6-1_6-2_oob_fixes.md](6-1_6-2_oob_fixes.md) (영향 범위 정밀 분석 포함)

## 전제 / 범위

- `__PROGRAM_MODE_REF_C__` (FER 성능 측정) 빌드의 속도만 개선한다. TV Gen / log 모드 성능은 대상 아님
- 실행 로직(연산 결과)은 바꾸지 않는다 — 항목별 bit-exact 여부는 checklist와 상세 문서에 명시
- HCU 버퍼 매핑 블록(C2V_Cal / V2C_Store 내 TV 가드 안쪽)은 어떤 항목도 건드리지 않는다

## patch 기준 버전

- `patches/*.patch`의 `original/` = 이 저장소 `0_LDPC_original/` 소스 (2026-07 시점), `revised/` = 항목 적용본(`1_LDPC_revised/`)
- patch는 항목당 하나, 누적이 아닌 **직전 항목 대비 해당 항목의 변경만** 포함
