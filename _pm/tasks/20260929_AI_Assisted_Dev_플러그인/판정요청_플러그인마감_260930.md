## 물음 1. 플러그인 저장소를 회사 GitHub에도 올릴 것인가

- 🔎 예시: 플러그인(Claude Code에 설치하면 스킬과 절차가 더해지는 기능 묶음)은 지금 개인 GitHub의 비공개 저장소 AI_Assisted_Dev에 올라가 있고, 판 0.1.0 표시(git 태그: 특정 시점의 저장소에 붙이는 이름표)도 붙어 있다. 동료 A가 회사 PC에서 이 플러그인을 설치하려 한다
  - 1️⃣ 이면: 사용자가 회사 GitHub에 저장소를 만들고 주소를 알려 준다. 제가 그 주소를 두 번째 원격(git이 복사본을 올리는 바깥 저장소)으로 등록해 같은 내용과 태그를 올린다. 동료 A는 Claude Code에서 설치 명령 두 줄(마켓플레이스 등록: 이 저장소를 플러그인 목록으로 등록하는 명령, 설치: 목록에서 플러그인을 고르는 명령)을 친다. 이후 고칠 때마다 판 번호를 올려 태그를 붙이면 동료의 Claude Code가 다음에 켤 때 새 판을 받는다
  - 2️⃣ 이면: 개인 GitHub에만 둔다. 동료 A는 접근 권한이 없어 설치하지 못한다. 사용자 본인은 이 PC의 폴더를 직접 가리키는 방식(`--plugin-dir`, 세션 하나에만 싣는 실행 옵션)으로 쓴다
- 📌 상황: 설치 안내(README)는 저장소 주소만 바꾸면 되게 적혀 있다. 판 표시는 저장소의 플러그인 목록 파일(`.claude-plugin/marketplace.json`)과 플러그인 정보 파일(`plugin/.claude-plugin/plugin.json`)의 판 번호가 같아야 만들어지고, 지금 둘 다 0.1.0이다
- ⚠️ 문제: 회사 GitHub 저장소는 사용자 계정으로만 만들 수 있고, 회사 규정(개인 계정의 업무 코드, 외부 도구 배포)은 제가 모른다
- ❓ 결정할 것
  - 1️⃣ (권고) 회사 GitHub에 올린다 (주소를 답에 적어 주십시오). 되돌리기 쉬움 (원격 등록 해제)
  - 2️⃣ 개인 GitHub에만 둔다
  - 권고 까닭: 플러그인의 목적이 동료에게 주는 것이다
  - 권고가 맞지 않는 경우: 회사에서 아직 시험해 볼 사람이 없거나 규정 확인이 먼저일 때

## 물음 2. 원본 2_LDPC_base의 실험 실행 파일이 폴더 이름 `2_LDPC_base`에 기대는 것을 지금 고칠 것인가

- 🔎 예시: 시험장 사본(플러그인을 실제 코드에 돌려 보려고 LDPC_dev의 `2_LDPC_base/`를 통째로 복사해 둔 폴더. 이름은 `ldpc_py`)에서 `workspace/test/` 폴더의 `python run.py`를 돌렸다 (2026-09-30 02:55, 플러그인의 온보딩 절차가 프로파일을 채우며 실제로 실행)
  - 실행 파일(설정 파일을 읽어 본체 코드를 부르는 짧은 파이썬 파일)이 부모 폴더로 올라가며 `2_LDPC_base/src` 폴더를 찾는다 (`workspace/test/run.py` 12행)
  - 폴더 이름이 `ldpc_py`라 못 찾고 `상위 폴더에서 2_LDPC_base/src를 찾지 못함`이라고 끝난다
  - 통합 저장소 작업(2026-08-26에 시작한, LDPC_dev와 논문 아카이브를 새 저장소 하나로 합치는 작업)에서는 이 폴더 이름을 `3_LDPC_base`로 바꾸기로 했다. 그때 다섯 실험 폴더의 `python run.py`가 모두 같은 이유로 멈춘다
  - 1️⃣ 이면: LDPC_dev의 `2_LDPC_base/workspace/{_template, base_run, test, matrix_sel_1_HD, matrix_sel_1_HD_fixed}/run.py` 다섯 파일의 12행 조건에 "이 저장소의 `src/run.py`가 있는 조상 폴더"도 허용하는 한 줄을 더한다. 폴더 이름이 무엇이든 `python run.py`가 돈다. 같은 난수 seed(난수 시작값. 같으면 결과가 같아야 한다)로 돌려 결과가 전과 같은지 확인한 뒤 커밋(변경 기록)한다. 고칠 범위는 파일 5개, 3줄씩. git으로 되돌리기 쉬움
  - 2️⃣ 이면: 지금은 두고 통합 저장소를 조립할 때 고친다. 그때까지 시험장 사본에서는 디코더를 바꿔 끼운 실험(변형 디코더 실험)을 못 돌린다
- 📌 상황: 원본 배치(`LDPC_dev/2_LDPC_base/`)에서는 지금도 동작한다. 문제는 폴더 이름이 바뀌는 순간(통합 저장소, 시험장 사본, 동료의 사본) 생긴다. 온보딩 절차가 시험장에 남긴 판정요청의 물음 1과 같은 내용이다
- ⚠️ 문제: 사용자 프로젝트의 실행 코드를 고치는 일이라(변경 등급 Review: 로직을 바꾸되 동작은 같게 두는 변경) 제가 진행하지 않았다
- ❓ 결정할 것
  - 1️⃣ (권고) 지금 LDPC_dev에서 고친다
  - 2️⃣ 통합 저장소를 조립할 때 고친다
  - 권고 까닭: 한 줄짜리 수정이고, 통합 저장소와 사본 양쪽에서 같은 명령이 통하게 된다
  - 권고가 맞지 않는 경우: 통합 저장소에서 실험 폴더 구조 자체를 다시 짤 계획이면 2️⃣

## 물음 3. 2_LDPC_base의 옛 리뷰 기록 11개 파일에 든 개인 계정 경로 15곳을 치환할 것인가

- 🔎 예시: `2_LDPC_base/_pm/done/20260806_review/r3_round3_lv2_verification/worker_a_3.md` 17행에 사용자 계정 이름이 든 드라이브 절대 경로가 적혀 있다 (온보딩 절차의 검증 작업자가 2026-09-30에 찾음). 같은 꼴이 `_pm/done/`과 `_pm/tasks/20260808_review/` 아래 11개 파일에 15곳 있다
  - 1️⃣ 이면: 15곳의 경로에서 계정 이름 앞부분만 `<루트>`로 바꾼다. 예: (지금) `D:\...\<계정>\...\2_LDPC_base\src\decoder.py` → (바꾼 글) `<루트>/2_LDPC_base/src/decoder.py`. 문장 뜻은 그대로다. LDPC_dev에 커밋(변경 기록)해 GitHub에서 보이는 최신 판에서는 사라진다. 다만 git은 옛 판도 이력으로 보관하므로 옛 판을 일부러 열면 남아 있다
  - 2️⃣ 이면: 그대로 둔다. "리뷰 기록 이력물은 손대지 않는다"는 2_LDPC_base의 방침을 우선한다
- 📌 상황: 2_LDPC_base에는 리뷰 기록 이력물을 보존하는 방침이 있다 (2026-08-09에 문서 전체의 줄표를 한꺼번에 고칠 때도 이력물은 뺐다). 한편 LDPC_dev의 문서는 회사 동료 등 다른 사람이 볼 수 있으므로 개인 경로를 넣지 않는다는 규칙이 있다. 통합 저장소로 옮기면 이 파일들이 그대로 회사 GitHub에 올라간다
- ⚠️ 문제: 두 방침이 부딪히므로 제가 정하지 않았다
- ❓ 결정할 것
  - 1️⃣ (권고) 계정 부분만 기계 치환한다 (파일 11개, 15줄. git으로 되돌리기 쉬움)
  - 2️⃣ 그대로 둔다
  - 권고 까닭: 치환은 문장 뜻을 바꾸지 않아 이력물 보존 취지와 어긋나지 않고, 통합 저장소가 회사에 올라가기 전에 지우는 편이 낫다
  - 권고가 맞지 않는 경우: 이력물은 글자 하나도 바꾸지 않기로 했다면 2️⃣
