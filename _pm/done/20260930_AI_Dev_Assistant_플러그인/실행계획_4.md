# AI_Assisted_Dev 플러그인 실행 계획 (4단계: idea-apply, speed-opt, robustness-check, param-opt)

> 작성: 2026-09-30
> 설계: [20260929_AI_Assisted_Dev_플러그인.md](20260929_AI_Assisted_Dev_%ED%94%8C%EB%9F%AC%EA%B7%B8%EC%9D%B8.md) 3절 스킬 표의 네 줄, 9절 4번
> 공통 제약은 1단계 계획과 같다. 코드는 저장소에 바로 쓴다 (테스트 먼저). 옮겨 올 원본: 3_LDPC_ideas의 새논문적용규칙.md와 _template/README.md와 실험로그.md, 1_LDPC_revised/docs/speed_opt/checklist.md와 항목 문서와 6-1_6-2 문서. 파라미터 최적화기는 원본 도구의 구조(파라미터 공간, 평가 함수 호출, 탐색 시퀀스, 병렬)만 옮기고 이름과 도메인은 옮기지 않는다

**목표:** 네 스킬이 프로파일(교체 지점, 성능 지표, 평가 방법)을 읽고 각자의 절차를 돈다. 아이디어 폴더와 현황표와 실험로그, 효율화와 안정성 점검표와 항목 문서, 파라미터 최적화기 뼈대가 스크립트로 만들어진다.

## 검토 초점

- 1. 현황표에 같은 번호를 두 번 넣지 않는다 (작업 1)
- 2. 점검표를 다시 만들어도 채운 항목 문서를 덮어쓰지 않는다 (작업 2)
- 3. 최적화기가 평가 명령 실패(종료 코드 0 아님, 지표 못 읽음)를 기록하고 멈추지 않는다 (작업 3)
- 4. 최적화기 기록(log.jsonl)이 있으면 이어 돌린다 (작업 3)
- 5. 평가 명령의 출력 인코딩이 콘솔과 달라도 지표를 읽는다 (작업 3)

## 파일 구조

```
plugin/scripts/idea_init.py               아이디어 폴더 + 현황표 행
plugin/scripts/checklist_init.py          점검표와 항목 문서 양식 복사 (speed | robustness)
plugin/scripts/param_opt_init.py          최적화기 뼈대 복사
plugin/templates/idea/README.md           아이디어 보고서 양식 (📌 요약, 📄 출처, 📊 지표 계획, 🔬 실험, ✅ 결론)
plugin/templates/idea/status_table.md     현황표 양식 (| # | 제목 | 출처 | 상태 | 디렉토리 |)
plugin/templates/idea/experiment_log.md   실험로그 양식 (최신이 위, 환경과 인사이트)
plugin/templates/checklists/speed/{checklist.md, item_template.md, README.md}
plugin/templates/checklists/robustness/{checklist.md, item_template.md, README.md}   항목 풀 포함
plugin/templates/param_opt/{config.json, optimizer.py, README.md}
plugin/skills/{idea-apply, speed-opt, robustness-check, param-opt}/SKILL.md
tests/test_idea_init.py, test_checklist_init.py, test_param_opt.py
```

## 작업 1: 아이디어 양식과 `idea_init.py`

**인터페이스:** `idea_init.create(root, ideas_dir, number, name, source) -> dict` (folder, readme, table_file, row_added: bool). 폴더 `{ideas_dir}/{번호 3자리}_{이름}/`에 README.md를 양식에서 만들고(제목과 출처 치환), `{ideas_dir}/README.md`의 현황표에 행을 더한다 (없으면 status_table 양식으로 만든다. 같은 번호가 있으면 더하지 않는다). `{ideas_dir}/실험로그.md`가 없으면 양식으로 만든다. `main(argv)`: `idea_init.py [--root .] [--dir ideas] 번호 이름 [출처]`.

**테스트:** `test_create_folder_readme_and_table_row`, `test_same_number_not_added_twice`, `test_cli_korean_name`.

## 작업 2: 점검표 양식과 `checklist_init.py`

**인터페이스:** `checklist_init.init(root, kind) -> int` (kind는 speed 또는 robustness. `docs/{speed_opt | robustness}/`에 checklist.md, item_template.md, README.md를 복사. 있는 파일은 건너뜀). `main(argv)`.

**양식 내용:**
- speed/checklist.md: 원칙(한 항목 = 한 커밋, 결과 동일성 표기: 결과 동일 보장 | 검증 필요, 위험도, 이 환경에서 빌드하지 않으면 외부 검증 기록), 단계(핫루프, 보조 경로, 자료 구조, 입출력) 절과 항목 꼴 `- [ ] **N-M. 제목** [결과 동일 보장 | 검증 필요 / 위험 낮음|중간|높음] 상세: [N-M_이름.md](N-M_이름.md)` 아래 `함수`, `바꿀 부분`, `방법` 줄
- speed/item_template.md: 표(상태, 파일, 결과 동일성, 위험도), 절 "왜 해야 하나", "무엇을 어떻게 바꿨나", "검증", "이식 앵커"
- robustness/checklist.md: 항목 풀 표(배열 범위 밖 접근, 정수 넘침, 초기화 안 된 값, 0으로 나눔, 고정소수점 포화와 자름, 재현성(seed, 실행 순서), 자원 해제, 입력 검증. RTL: 리셋 값, 비트 폭 불일치, 클록 영역 넘김, 래치 생성, X 전파)와 프로젝트에 맞게 고른 항목을 적는 절. 항목 꼴은 speed와 같되 `[결과 달라질 수 있음]` 표기와 "적용 시점: 최적화 항목과 커밋을 섞지 않는다"
- robustness/item_template.md: 표(상태, 파일, 분류, 결과 영향, 적용 시점), 절 "재현", "영향 범위 분석", "무엇을 어떻게 바꿨나", "검증", "이식 앵커"

**테스트:** `test_init_speed_and_robustness_copy_once`, `test_unknown_kind_returns_error`.

## 작업 3: 파라미터 최적화기 뼈대와 `param_opt_init.py`

**뼈대 (`templates/param_opt/`):**
- `config.json`: `{"params": [{"name": "alpha", "type": "float", "min": 0.5, "max": 1.0, "step": 0.05}, {"name": "mode", "type": "choice", "values": ["a", "b"]}, {"name": "depth", "type": "int", "min": 1, "max": 8}], "evaluate": {"command": "python sim.py --alpha {alpha} --mode {mode} --depth {depth}", "metric_regex": "FER=([0-9.eE+-]+)", "minimize": true, "timeout_seconds": 600}, "search": {"budget": 50, "workers": 1, "seed": 0, "initial": "random", "local_ratio": 0.5}}`
- `optimizer.py` (표준 라이브러리): 설정 검증, 후보 생성(무작위 + 최량점 주변 국소 변이), 평가(명령 실행, 정규식으로 지표 읽기, 실패는 `null` 기록), 기록(`log.jsonl`에 한 줄씩, 다시 돌리면 이어서), 병렬(`workers`만큼 `concurrent.futures`), 결과(`best.json`과 표). 명령의 출력은 바이트로 받아 UTF-8로 풀되 실패하면 콘솔 인코딩으로 다시 푼다
- `README.md`: 사용법, 설정 항목 풀이, 결과 읽는 법

**인터페이스:** `param_opt_init.init(root, dir_name="optim") -> int`. optimizer의 함수: `load_config(path)`, `validate(config) -> list[str]`(오류 문장), `sample(params, rng)`, `mutate(best, params, rng)`, `evaluate(config, point) -> float|None`, `run(config_path, budget=None) -> dict`.

**테스트 (`tests/test_param_opt.py`):** 평가 명령은 `python -c` 한 줄(예: `(x-0.3)**2` 출력)로 둔다.
- `test_validate_reports_missing_fields`
- `test_random_then_local_search_improves_best` (budget 30, seed 고정, best의 x가 0.3에서 0.05 안)
- `test_failed_command_is_logged_as_null_and_run_continues`
- `test_resume_skips_evaluated_points` (log.jsonl에 3점 있으면 이어서 budget까지)
- `test_metric_read_from_cp949_output` (명령이 cp949 바이트를 내도 지표를 읽음)

## 작업 4: 스킬 넷

- idea-apply: 절차 1. 접수(현황표에 행, 폴더 생성: `idea_init.py`), 2. 설계(README의 📌 요약 네 가지와 📊 지표 계획 표를 코드 작성 전에 채움), 3. 붙이기(프로파일 replacement_points.md의 교체 단위와 4절 절차대로. 교체 지점이 없으면 먼저 만드는 작업을 pm 스킬로 등록하고 멈춤), 4. 실행과 비교(기준 실험과 같은 조건, on/off), 5. 기록(README 🔬 실험과 ✅ 결론, 실험로그 맨 위에 환경과 인사이트, 현황표 상태를 실험중에서 성공|실패|폐기로), 6. wiki 스킬에 넘길 것(교훈은 trials, 반영되면 decisions). 규칙: 본체에 아이디어 코드를 넣지 않는다, 재정의 함수의 인자 목록은 부모와 같게, 문서에 날짜를 적지 않는다(실험로그만 절 제목에), 용어는 첫 등장에서 풀이
- speed-opt: 절차 1. 후보 발굴(프로파일 structure의 핫루프와 자료 구조, 필요하면 explore), 2. 점검표 작성(`checklist_init.py speed`, 항목마다 함수와 바꿀 부분과 방법과 결과 동일성 표기), 3. 한 번에 한 항목: 수정, 항목 문서, 결과 동일성 근거, 사용자 검토, 커밋, 4. 외부 검증 기록(같은 seed 결과 동일. 이 환경에서 빌드하지 않으면 검증 위치와 방법을 적음), 5. README 적용 이력 표 갱신
- robustness-check: 절차 1. 항목 풀에서 프로젝트 언어에 맞는 항목 고르기(`checklist_init.py robustness`), 2. 항목마다 재현(테스트나 입력 만들기), 3. 영향 범위 분석(타이밍, 중간값, 최종 결과 중 무엇이 달라지는지 전수 추적), 4. 수정(결과가 달라지면 새 값이 맞는 이유를 적음), 5. 커밋은 최적화와 분리, 6. 테스트를 남긴다(재현 입력을 회귀 테스트로)
- param-opt: 절차 1. 프로파일 overview의 성능 지표와 평가 방법 확인, 2. `param_opt_init.py`로 뼈대, 3. config.json에 파라미터 공간(이름, 형, 범위)과 평가 명령(자리표시 `{이름}`)과 지표 정규식 채우기, 4. budget 3으로 시험 실행, 5. 본 실행(workers는 PC 코어 수 안에서), 6. best.json과 결과 표를 README에, 실험로그에 환경과 인사이트
