## 2. 초안 속 물음에 대한 답

### 2.1 "agent라고 썼는데 .md의 description과 무엇이 다른가"

Claude Code 플러그인의 구성 요소는 세 가지이고, 셋 다 md 파일이며 셋 다 description 필드를 가진다. 다른 것은 실행 방식이다.

| 구성 요소 | 파일 | 누가 부르나 | 어디서 도나 | 맞는 용도 |
|---|---|---|---|---|
| 스킬(skill) | `skills/{이름}/SKILL.md` | 사용자가 `/이름`으로 부르거나,<br>description이 상황에 맞으면 Claude가 스스로 | 지금 대화 안 (같은 문맥) | 절차, 점검표, 규칙 |
| 명령(command) | `commands/{이름}.md` | 사용자만 | 지금 대화 안 | 옛 방식. 새로 만들 때는 스킬 |
| 에이전트(agent) | `agents/{이름}.md` | Claude가 위임하거나 사용자가 `@이름`으로 | 별도 문맥 (새 대화창처럼 독립,<br>결과만 돌아옴) | 읽을 것이 많고 오래 걸리는 일,<br>병렬 작업, 도구 제한, 다른 모델 |

- ㉮ 결론: "agent"는 더 있어 보이는 이름이 아니라 실행 방식이 다른 것이다. description은 "언제 이것을 쓰나"를 Claude가 고르는 기준이고 셋 다 있다
- ㉯ 초안의 1번부터 6번은 대부분 절차이므로 스킬이 맞다. 에이전트가 맞는 부분은 논문 여러 편을 병렬로 분석하는 작업자, 코드베이스를 관점별로 나눠 읽는 탐색 작업자처럼 문맥을 따로 쓰는 편이 나은 곳뿐이다
- ㉰ 에이전트 파일의 머리말 필드: name, description, model, tools, disallowedTools, skills, maxTurns 등. 스킬 파일의 머리말 필드: description, allowedTools, model, invoke(사용자만, Claude만, 둘 다)
- ㉱ 근거: Claude Code 문서 plugins/components (https://code.claude.com/docs/en/plugins/components.md)

### 2.2 "ldpc_dev에 논문 서치 tool이 있는가"

형제 저장소 LDPC_Paper_Analysis(원격 이름 ECC_papers)를 확인했다.

- ㉮ 있는 것
  - ㉠ 수집 결과: arXiv 1,124편과 IEEE 21,101편, 합계 22,225편의 메타데이터(`data/papers.db`). 수집은 완료로 닫혔고 수집 코드는 제거됐다
  - ㉡ PDF 내려받기 스크립트: `tools/arxiv_download.py`, `tools/ieee_downloader/` (1차 선별 통과분만)
  - ㉢ 1차 선별 병렬 워크플로: `src/stage1/review.py`, `src/stage1/select_workflow.js`, 기준서 `criteria/stage1/selection_criteria.md`
  - ㉣ 심층 분석 프롬프트와 분류 스키마: `criteria/stage3/analysis_prompt.md`, `criteria/stage3/categories.md` (이식성 상중하 같은 고정 선택지 표)
  - ㉤ 카탈로그와 진행맵 생성: `src/report/catalog.py`, `src/report/progress.py`. 탐색기: `docs/papers.html`
- ㉯ 없는 것: 주제를 주면 arXiv나 IEEE를 새로 검색하는 도구. 특허 검색은 전혀 없다
- ㉰ 뜻: 초안 3번의 "분류, 분석" 절반은 이미 있고 "검색" 절반은 새로 만들어야 한다. 검색 통로는 판정요청 물음 5

### 2.3 "code refactoring이 1_LDPC_revised에 있는가"

- ㉮ 있다. 속도 최적화 항목 36개(2-1부터 6-2까지)가 적용 완료 상태이고, 항목마다 문서 한 편(왜, 어떻게, 주의, 검토 상태)이 `1_LDPC_revised/docs/speed_opt/`에 있다

## 4. 빠진 것 (초안에 없는데 있어야 하는 것)

### 4.1 범용 부분과 도메인 부분의 분리 (가장 큰 것)

- ㉮ 초안 3, 4, 5번은 LDPC와 NAND 전용 내용이 깊이 박혀 있다. 선별 기준은 "NAND 바이너리 LDPC에 이식 가능한가"이고, 교체 지점 표는 BaseDecoder의 함수 6개이며, DAO는 LLR matrix 전용이다
- ㉯ 다른 문제를 다루는 엔지니어에게 주려면 "절차와 양식"(범용)과 "기준과 코드 지식"(도메인)을 나눠야 한다
- ㉰ 답은 논문 분석이 이미 쓰는 방식에 있다. `analysis_prompt.md`는 코드를 열지 않고 프로파일 한 파일(`paper_screening_profile.md`)만 읽고 판정한다. 이것을 일반화해 "프로젝트 프로파일"(플러그인이 첫 실행 때 사용자 코드에서 뽑아 만드는 문서 한 벌: 문제 정의, 코드 구조, 교체 지점, 보유 기법, 금지 사항)을 두면 스킬은 범용이 되고 프로파일만 프로젝트마다 다르다
- ㉱ 판정요청 물음 1

### 4.2 시작 스킬 (온보딩)

- ㉮ 초안 2-2가 말하는 "/init보다 나은 첫 이해"가 이것이다. 프로젝트 프로파일, 프로젝트 CLAUDE.md, `_pm/` 뼈대, `docs/` 뼈대를 한 번에 만든다
- ㉯ 초안 2번과 6번의 출발점이며, 다른 모든 스킬이 이 산출물 위에서 돈다

### 4.3 문서 사이의 링크와 태그 규약

- ㉮ "노션처럼 문서 간 링크를 보여 준다"는 것은 역링크(어떤 문서가 이 문서를 가리키는지) 표시다. 그러려면 ㉠ md 파일 머리말(파일 맨 앞의 제목, 태그, 관련 문서 목록)과 ㉡ 모든 md의 링크를 읽어 역링크 표를 만드는 스크립트가 있어야 한다
- ㉯ 지금 render.py는 md 링크를 html 링크로 바꾸기만 하고 링크 그래프를 만들지 않는다
- ㉰ 대시보드의 문서 지도가 여기서 나온다. 판정요청 물음 4

### 4.4 대시보드의 자료 흐름

- ㉮ 대시보드는 정적 html(GitHub Pages)이므로 "무엇을 보여 줄지"보다 "무엇에서 뽑을지"가 먼저다
- ㉯ 뽑을 곳 후보: `_pm/TODO.md`와 `DONE.md`(작업), 판정요청의 미답 물음(결정 대기), 아이디어 현황표(`3_LDPC_ideas/README.md`), 실험로그, 문서 링크 그래프
- ㉰ 스크립트가 뽑으려면 파싱 규칙이 정해진 md 양식이 있어야 한다. 지금 `_pm/` 문서는 사람이 읽는 양식이라 표 열 이름과 체크박스 꼴을 고정해야 한다
- ㉱ 통합 저장소 태스크의 판정 3번에서 "메인과 공간 페이지는 손으로 만든다"고 답했는데, 대시보드는 손으로 만들면 곧 낡으므로 그 답과 조율이 필요하다. 판정요청 물음 7

### 4.5 검색 도구의 외부 연결

- ㉮ 무료 API(응용 프로그램 인터페이스, 프로그램이 서비스에 질의하는 통로): arXiv API(키 없음), OpenAlex(학술 메타데이터, 키 없음), Semantic Scholar(키 선택). IEEE Xplore API는 키가 필요하고 사내 구독에 따라 다르다
- ㉯ 특허: USPTO PatentsView(미국 특허청, 무료), EPO OPS(유럽 특허청, 등록 필요), KIPRIS(한국 특허정보원, 키 필요). Google Patents는 공식 API가 없다
- ㉰ Claude Code의 WebSearch 도구로도 되지만 결과가 매번 다르고 수백 편은 못 다룬다
- ㉱ 사내 망이 외부 API를 막으면 어느 것도 못 쓴다. 사내 확인이 필요하다. 판정요청 물음 5

### 4.6 플러그인 검증과 배포

- ㉮ 구조 검사: `claude plugin validate`
- ㉯ 동작 검사: `claude plugin eval`. `evals/` 폴더에 사례마다 `prompt.md`(지시)와 `graders/`(채점 기준)를 두면 자동으로 여러 번 돌려 점수를 낸다. 근거: https://code.claude.com/docs/en/plugin-evals.md
- ㉰ 사용량 보기: `/skill-doctor` (스킬별 7일 사용량과 토큰 비용, 한 번도 안 불린 스킬 경고)
- ㉱ 배포: 로컬 시험은 `claude --plugin-dir ./플러그인폴더`, 공유는 marketplace.json을 사내 GitHub에 올려 `/plugin install`. `plugin.json`의 version을 올리면 다음 세션에서 자동 갱신된다. 근거: https://code.claude.com/docs/en/plugins/create.md
- ㉲ 초안에는 검증과 배포가 없다. 첫 판부터 `evals/` 사례를 스킬마다 하나씩 두는 편이 좋다

### 4.7 개인 설정과 공유할 규칙의 분리

- ㉮ 홈 폴더 CLAUDE.md에는 공유 가능한 규칙(존댓말, 결정 방식, 문서 검사 루틴, `_pm/` 규약)과 개인 설정(텔레그램 토큰, 로컬 경로, 형제 프로젝트 동기화)이 섞여 있다
- ㉯ 플러그인에는 앞의 것만 들어가고 뒤의 것은 각자의 홈 설정에 남는다. 알림 통로는 플러그인이 "설정되어 있으면 쓴다"로 두면 된다

### 4.8 superpowers 플러그인과의 겹침

- ㉮ 사용자 홈에 superpowers 6.4.1이 설치되어 있고 brainstorming, 계획 작성과 실행, 코드 리뷰, 디버그를 담당한다
- ㉯ 홈 prompts의 plan.md, review.md, debug.md, test.md와 역할이 겹친다. 어느 쪽을 쓸지 정하지 않으면 같은 요청에 스킬 둘이 함께 뜬다. 판정요청 물음 6

### 4.9 기밀

- ㉮ 플러그인은 배포물이므로 H-matrix, LLR 파일, 평가 대상 파라미터 같은 데이터가 예시로라도 들어가면 안 된다
- ㉯ 프로젝트 CLAUDE.md의 문장 작성 규칙 ㉲(입력 파일의 성격을 서술하지 않는다)와 같은 취지의 검사가 플러그인 저장소에도 필요하다

### 4.10 말

- ㉮ 지금 프롬프트와 규칙은 전부 한국어다. 대상이 사내 동료면 한국어로 두고 영어판은 뒤로 미룬다 (1절 ㉲의 가정)

## 5. 더할 것 (초안 항목을 구체화)

- ㉮ 1 대시보드: 보여 줄 칸 5개(작업, 결정 대기, 아이디어 현황, 최근 실험, 문서 지도). 스크립트 순서는 md에서 json을 뽑고 json으로 html을 만든다. 렌더 뒤 상대 링크 검사는 통합 저장소 태스크의 설계를 그대로 쓴다
- ㉯ 2 문서화: 결과물을 세 벌로 나눈다. ㉠ AI용(프로젝트 프로파일, 의존 지도, 교체 지점 표), ㉡ 사람용(README, 시작 안내, architecture, ADR), ㉢ 색인(태그, 역링크). 탐색 스킬은 explore.md를, 위키화 스킬은 wiki.md를 옮긴다
- ㉰ 3 조사: 단계 4개(검색, 1차 선별, 심층 분석, 아이디어 접수)를 스킬 4개로 나눈다. 기준서는 빈칸 양식으로 주고 프로파일에서 채운다. 분류 스키마는 categories.md의 고정 선택지 표를 일반화한다
- ㉱ 4 아이디어 적용: 새논문적용규칙의 "교체 지점" 개념을 일반화한다. 사용자 코드에 교체 지점이 없으면 만드는 단계를 첫 단계로 둔다. 실험로그와 현황표 양식을 제공하고, 성공과 실패의 교훈을 위키에 누적한다
- ㉲ 5 최적화: 두 갈래로 나눈다. ㉠ 코드 효율화는 체크리스트, 항목별 문서, 한 번에 한 항목, 외부 검증 기록. ㉡ 파라미터 최적화는 DAO의 구조(파라미터 공간 정의, 평가 함수 호출, 탐색 시퀀스, MPI 병렬)를 사용자 시뮬레이터에 맞춰 생성하는 뼈대. DAO 자체는 LDPC 전용이라 참조 구현으로만 둔다
- ㉳ 6 프로젝트 관리: `_pm/` 규약 그대로. 세션 시작 자동 실행(TODO 읽고 시각 기록), 작업 완료 알림(알림 통로는 선택 설정), 판정요청 스킬(decision.md)

- ㉮ "agent" 낱말: 스킬로 바꾸고 에이전트는 병렬 작업자에만 쓴다 (2.1절)
- ㉯ 항목 번호 순서가 만드는 순서와 다르다. 의존 관계는 6(관리 규약)과 2(문서화, 프로파일)가 먼저, 그 다음 1(대시보드는 이 둘의 산출물을 보여 줌), 그 다음 4(아이디어 적용은 프로파일과 실험 양식이 필요), 그 다음 3(조사는 4의 접수 양식으로 이어짐). 5(최적화)는 독립이다

- ㉲ 5-1 "여기 있는지는 모르겠다": 있다 (2.3절)
